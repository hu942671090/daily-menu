# 关键假设与待办事项

## 一、关键假设

1. **日期口径**：默认时区 `Asia/Shanghai`，一周从周一开始；「今天」「本周」均按目标时区的本地日期计算。
2. **餐次配置**：早餐 1 道、午餐 2 道、晚餐 2 道；午餐/晚餐允许继续添加，最多 5 道。`SLOT_TARGETS` 集中定义，修改即可调整。
3. **游客模式**：不登录、不收集个人信息；偏好、收藏、周菜单、购物清单勾选只保存在当前端本地。
4. **推荐依据**：只使用用户显式设置的偏好与菜谱自身属性，不推断健康、疾病或营养结论；菜谱文案不包含保健功效。
5. **视频相关性**：以 bilibili 公开接口返回的标题是否包含完整菜名为主要依据，属于「标题关键词匹配」，未逐帧核对做法；界面明确标注。
6. **图片性质**：全部为脚本生成的示意图（Pillow 绘制），不是实拍；每张图带「示意图 · 非实拍」水印，数据结构中也带 `kind/credit/note`。
7. **内容许可**：菜谱文字与示意图标注 CC BY 4.0；视频仅外链到平台原页，不下载、不转存。
8. **无外部密钥也能跑**：本地内容随包内置，API 不可用时 Web 自动回落内置数据，小程序完全离线可用（图片除外）。
9. **数字用量**：按人数比例换算后做单位友好取整（克/毫升、个数、勺），「少许/适量」永远保留文字。
10. **数据规模**：25 道菜谱用于演示推荐多样性；推荐器不依赖特定菜谱数量，但内容过少时会重复并在界面提示。

## 三、已知技术限制

1. **SMB 共享目录不支持符号链接**：因此没有使用 workspace；如迁移到本地 NTFS，可改为 pnpm workspace 并把路径别名替换为包依赖。
2. **小程序未在真实开发者工具/真机运行过**：本轮用 Node 模拟 `wx`/`Page` 环境验证了页面逻辑与持久化，但渲染、真机字体、图片域名校验仍需在微信开发者工具中确认。
3. **无 `Intl` 时区能力时的兜底**：小程序基础库缺少完整 `Intl` 时，仅 UTC/上海/香港/新加坡/东京使用固定偏移；伦敦/纽约会回落到设备本地时间，存在夏令时偏差。
4. **示意图形似度高**：同一菜系的插图风格接近，不能替代实拍；正式内容必须替换。
5. **视频封面未使用**：平台封面有防盗链，直接引用会裂图；界面用平台色占位，点击打开原视频，避免误导。
6. **搜索相关性**：菜名/食材匹配为字符串包含，未做拼音、同义词与错别字纠错；后续可接入分词或搜索服务。
7. **并发与性能**：内容规模小，推荐在客户端同步计算（毫秒级）；内容量大幅增长后应改为服务端缓存 + 分页。
8. **浏览器兼容**：在 Edge（Chromium）1440px 与 390px 视口验证；未覆盖 Safari/iOS 实机，CSS 已使用主流特性并提供降级。
